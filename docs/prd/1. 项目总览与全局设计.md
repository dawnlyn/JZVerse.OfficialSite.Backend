# 1. 项目总览与全局设计 
## 1.1 项目背景
本平台定位为一站式互联网服务聚合平台，集成多元内容与工具服务，满足用户信息获取、内容创作、学习娱乐、资源管理等综合需求。支持Web端、移动端（iOS/Android）、PC端（Linux/Windows/Mac）、TV端及微信/支付宝等小程序端，采用响应式设计确保跨平台用户体验一致性。
## 1.2 目标用户画像
### 1.2.1 求知若渴的“数字原生代”学生与技术爱好者
- 年龄段：18-24岁（大学生及研究生、初入职场的00后）。
- 核心特征：成长于互联网时代，习惯线上获取一切信息；对新技术敏感，有强烈的自我提升和探索欲；时间相对充裕，但经济能力有限。
- 痛点：
	- 信息过载与筛选困难：面对海量学习资源（教程、开源项目）不知从何入手，难以辨别质量。
	- 实践机会与成果展示匮乏：学了理论知识，但缺乏真实的项目练手机会，也没有好的平台展示自己的作品（代码、设计、文章）。
	- 社交圈层局限：在现实校园或工作中，难以找到志同道合的技术伙伴或学习搭子。
- 核心需求：
	- 一站式知识获取与技能提升：高效地找到优质、免费或低成本的教程、文档、开源代码。
	- 实践、分享与获得反馈：拥有一个可以发布个人项目、撰写技术博客、并获得同行评价的“数字简历”平台。
	- 融入兴趣社群与拓展人脉：进入论坛社区和开源仓库，参与讨论、协作，建立专业网络。
- 典型使用场景：
	1. 为了完成课程作业或毕业设计，在在线教育模块看教程，在维基百科查概念，最后在开源仓库寻找类似项目参考。
	2. 自学了一门新编程语言后，在工具集合里找好用的开发工具，然后在项目公示板块发布自己的练手小项目，并到相关论坛社区发帖求指导。
	3. 课余时间，在游戏库寻找独立游戏，在在线观影模块看科技纪录片，在好物推荐里种草性价比高的数码配件。
### 1.2.2 追求品质与效率的“都市乐活”白领与中产 (核心用户)
- 年龄段：25-40岁（已步入职场数年，处于事业上升期或稳定期，可能已组建家庭）。
- 核心特征：生活节奏快，工作压力大；消费能力强，注重生活品质与时间效率；有明确的兴趣爱好和审美追求。
- 痛点：
	- 时间碎片化与精力分散：想学习新技能（如烹饪、乐器）、休闲娱乐，但难以抽出整块时间，且需要在多个APP间切换。
	- 消费决策成本高：面对琳琅满目的商品和服务（从家电到课程），需要花费大量时间比价、看评测，担心“踩坑”。
	- 缺乏深度社交与兴趣圈：现实社交圈固化，难以基于纯粹的兴趣爱好结识新朋友。
- 核心需求：
	- 高效整合的“生活解决方案”：在一个平台内，就能满足学习（在线教育）、娱乐（音乐、观影、阅读）、生活（食谱）、购物（商城、好物推荐）等多元需求，节省切换成本。
	- 可信的消费指南与决策支持：依赖好物推荐（来自真实用户或专业测评）和社区论坛的口碑来做购买决策。
	- 精神滋养与兴趣社交：在画廊欣赏艺术，在在线阅读模块读一本好书，并在对应的博客社区中找到同好交流心得。
- 典型使用场景：
	1. 周末想在家做一顿大餐，先在在线食谱找菜谱，根据清单在在线商城下单食材。等待时，在在线观影刷一部剧。
	2. 计划购买一台投影仪，会重点浏览好物推荐板块的横向评测，并去相关产品的论坛社区看真实用户反馈。
	3. 晚上睡前，打开在线音乐听助眠歌单，或在在线阅读模块看几章小说放松。
### 1.2.3 热衷创作与分享的“斜杠”内容创作者与独立开发者
- 年龄段：22-35岁（可能是自由职业者、小型工作室成员、或有一技之长的上班族）。
- 核心特征：拥有某项专业技能（如写作、编程、设计、视频制作）；不满足于单一职业身份，渴望建立个人品牌；深度依赖互联网进行创作、协作与变现。
- 痛点：
	- 作品发布与推广渠道分散：作品（文章、代码、设计图、视频）分散在多个平台，不利于个人品牌集中展示和粉丝积累。
	- 缺乏稳定的协作与反馈环境：个人创作易陷入瓶颈，需要团队协作或高质量的同行反馈来突破。
	- 工具链复杂与资源管理混乱：创作过程中使用的工具、素材、参考资料散落各处，管理效率低。
- 核心需求：
	- 个人品牌的全方位展示中心：将个人博客、项目作品集（画廊/项目公示）、开源代码仓库等整合在一个主页下，形成强大的个人名片。
	- 深度互动与价值交换的社区：在垂直的论坛社区中与粉丝、客户、合作伙伴进行深度交流，获取灵感、合作机会甚至直接变现。
	- 提升创作效率的工具与资源库：便捷地使用工具集合，将创作素材存储在在线网盘，并通过网址导航快速访问常用资源站。
- 典型使用场景：
	1. 一名独立开发者，将最新的开源项目代码提交到平台的开源仓库，在项目公示页写详细说明文档，并同步到自己的技术博客。通过留言反馈收集用户问题。
	2. 一名插画师，在画廊模块发布系列作品，在博客社区分享创作过程，并通过好物推荐关联自己使用的绘画工具购买链接。
	3. 一个两人小团队，使用平台的在线网盘共享设计稿和文档，在论坛社区的“找合作”板块招募兼职程序员，并通过后台管理功能查看作品的数据表现。
## 1.3 核心价值主张
### 1.3.1 对用户
- 省时：一站式聚合，免去在数十个独立App间切换的繁琐。
- 省心：基于AI的深度个性化，让信息和服务主动找到用户。
- 增值：跨业务场景联动（如看资讯-\>买课程-\>社区讨论），创造连贯体验与额外价值。
- 归属：基于地理和兴趣的社区，重建线上邻里关系与社交归属感。
### 1.3.2 对生态伙伴（服务商/开发者）
- 流量入口：接入平台，即可触达海量、精准的本地生活与消费用户。
- 技术赋能：平台提供统一账户、支付、数据等中台能力，降低开发与运营成本。
- 生态协同：与平台内其他服务形成交叉引流，提升用户生命周期价值。

## 1.5 架构设计与技术实现
### 1.5.1 架构设计
- 技术栈采用前后端分离，Web端采用Nuxt.js及Vue.js全家桶，后端采用C# Asp.Net Core 官方全家桶，非必要不使用第三方框架，其他平台采用MAUI跨平台。
- 微服务架构：
- 身份认证服务：独立部署的身份认证微服务，负责用户注册、登录、令牌管理
- 用户中心服务：管理用户资料、偏好设置、隐私配置
- 推荐引擎服务：实时计算个性化推荐，支持AB测试和算法迭代
- 搜索服务：基于Elasticsearch的全文搜索服务，支持多维度检索
- 消息推送服务：统一的消息聚合与推送服务，支持多通道推送
- API网关：统一入口的API网关，负责路由转发、限流、鉴权
- 一个模块一个服务
数据存储设计：
- 在优先考虑性能的情况下，选用尽可能少的数据库，如果一个服务使用数据库A和数据库B性能接近，但使用数据库B的服务更多，则选用数据库B；相反，如果数据库A比数据库B快很多，则选用A。快慢判断标准为用户明显可感知差异的程度。数据量级为TB级。
- 以下数据库对应的使用场景仅做参考，不做要求，所有场景优先考虑PostgreSQL。
- 关系型数据库（PostgreSQL）：存储用户核心数据、关系数据、事务数据
- 文档数据库（MongoDB）：存储用户行为日志、内容数据、个性化配置
- 缓存层（Garnet）：会话缓存、热点数据缓存、推荐结果缓存
- 搜索引擎（Elasticsearch）：全文搜索索引、日志分析
- 对象存储（S3兼容）：用户上传的文件、图片、视频等多媒体资源
- 图数据库（Neo4j）：社交网络、推荐引擎（关系网）、欺诈检测、知识图谱
- 时序数据库（InfluxDB）：监控
- 向量数据库（Milvus）：AI、语义搜索、图像/视频/音频检索、推荐引擎（相似度）
### 1.5.2 关键技术实现
- 性能优化：
- 前端性能：
	- 所有列表虚拟滚动，支持数千项目流畅展示
	- 图片懒加载和渐进式加载
	- 组件级代码分割，按需加载
- 后端性能：
	- 推荐结果预计算和缓存，减少实时计算压力
	- 数据库读写分离且分库分表，热点数据缓存
	- CDN加速静态资源和多媒体内容
	- AB测试框架：支持多算法并行测试，实时评估效果
- 跨场景数据同步：
	- 同步协议：基于WebSocket的实时双向同步
	- 冲突解决策略：
		- 最后写入优先（LWW）：适用于大多数场景
		- 操作转换（OT）：适用于协同编辑场景
		- 人工合并：复杂冲突提供合并界面
	- 离线支持：Service Worker实现离线缓存，重新联网后增量同步
	- 事件驱动：各模块会订阅及发布各种事件，用以通知到其他模块，例如用户信息变更或用户发布内容、购买商品等操作
- 配置热更：
	- 使用配置中心（如Nacos, Apollo, Consul）。将所有可动态调整的配置（令牌有效期、密码策略）存入配置中心。认证服务监听配置变化，实时生效。
	- 支持配置的灰度发布、特性开关、一键回滚，并具备完善的权限审计日志：
		- 基于特性开关服务（如LaunchDarkly或自研系统）实现。
		- 一个新功能（如“人脸识别登录”）的发布路径为：
			1. 对内部员工100%开放
			2. 对1%的白名单用户开放
			3. 对10%的全国用户开放
			4. 全量发布
		- 在开关平台一键将特性关闭，所有用户立即切回旧逻辑，实现秒级回滚。
- GDPR属地要求：
	- 欧盟用户的数据物理存储在欧盟的数据中心。其他地区（如北美、亚洲）同理。
	- 平台逻辑上为“全球服务”，但技术上由多个区域性实例组成。用户注册时根据其IP地址或选择归属地分配到相应实例。禁止将欧盟用户数据同步或传输至欧盟以外的服务器。平台内部需建立严格的数据跨境传输审批流程。
- 所有重试机制采用指数退避
- 数据库迁移：
	- 流程（以增加字段为例）：
		1. 部署支持新老Schema的代码；
		2. 执行ALTER TABLE ...迁移；
		3. 后台任务异步回填数据；
		4. 部署只依赖新Schema的代码；
		5. （可选）在业务低峰期删除旧字段。使用gh-ost等工具实现，避免锁表。
## 1.6 全局用户体验
- 情感化设计与空状态：
	- 文档中缺少对“空状态”的设计。例如，新用户首次进入首页，除了引导流程，空白的“我的服务”区域应有生动的插图和提示文字，如“这里将展示您最常用的服务，快去探索一下吧！”，并提供一个明显的“探索服务”按钮。
	- 识别“浏览者”的特征（如登录频繁但功能使用单一）：
		- 通过站内信或推送，发送个性化邀请，如“您关注的技术领域有一个新的热门社群，要不要去看看？”或“发现一个能提升您工作效率的XX工具”。
		- 与积分、勋章等成长体系结合，完成特定探索任务可获得奖励。
- 多语言和国际化支持：
	- 第一层（静态文本）：界面元素使用i18n标准方案，资源文件与代码分离。
	- 第二层（动态内容）：服务卡片的标题、描述等由接入方通过API提供多语言版本，平台按用户语言偏好请求对应内容。
	- 第三层（AI生成内容）：推荐理由等由AI生成的内容，在生成时即指定语言。这是一个渐进式过程，优先覆盖主要语种。
- 设备兼容性：
	- Chrome/Firefox/Safari/Edge最近三个主流版本，需测试国产浏览器
	- 移动端需覆盖iOS 13+和Android 8+的常用机型
- 超越WCAG标准，制定团队内部的详细规范（A11y）规范：
	- 键盘导航逻辑：所有交互元素必须具有清晰的:focus状态，Tab键顺序符合逻辑。
	- 屏幕阅读器适配：为关键动态区域（如服务卡片、消息通知）设置正确的ARIA标签（aria-label, aria-live），向视障用户清晰地传达变化。
	- 颜色与对比度：不仅满足标准，还要确保在单色打印或色盲用户看来，信息依然有效。例如，错误信息不能仅用红色表示，还应配有图标或文字。
	- 无障碍体验测试：
		1. 工具自动化扫描（如axe, WAVE）
		2. 核心流程的手动屏幕阅读器测试（如NVDA, VoiceOver）
		3. 邀请真实残障用户参与可用性测试。
- 关键指标体系（OKR / North Star Metric）：
	- 北极星指标：每周使用超过3个不同模块的活跃用户数代表平台的成功，这直接体现了平台价值的实现程度。
	- 关键目标：
		- 提升新用户首次登录后7日内添加快捷方式的比率。
		- 降低用户通过搜索找到目标服务的平均耗时。
		- 提升推荐服务卡片的点击通过率（CTR）。
- 用户旅程分析与漏斗模型：
	- 建立核心用户旅程的漏斗，如 首页曝光 -\> 点击服务卡片 -\> 服务内关键操作完成。分析每个环节的流失率，定位体验瓶颈。
	- 使用Session Replay（会话回放）工具，随机抽取失败会话，直观地看用户在哪里困惑或受挫。
## 1.7 系统安全
- 传输安全：全站HTTPS，敏感接口额外加密
- 访问控制：API访问频率限制和防刷机制，并且为每个第三方接入服务分配AppKey/AppSecret和严格的权限范围（Scope）
- 前端安全漏洞：
	- 对所有用户输入进行转义（如使用DOMPurify库）。
	- 部署严格的内容安全策略，只允许执行来自可信源的脚本，内联脚本无效，从根本上遏制XSS。
	- 强制使用现代前端框架（React/Vue）的数据绑定方式，避免直接操作innerHTML。
- 安全监控：
	- 实时异常行为检测
	- 安全日志集中审计
	- 定期安全扫描和渗透测试
	- 告警分级：
		- P0（致命）：核心功能不可用，需立即呼叫（如登录失败）。目标：5分钟内响应。
		- P1（严重）：功能严重受损，需2小时内处理（如搜索响应慢）。
		- P2（警告）：非核心功能异常，次日处理即可（如头像上传失败）。
	- 告警升级：P0告警15分钟未认领，自动升级并通知团队负责人；30分钟未解决，通知总监。
- 容器化部署的敏感配置管理：使用K8s Secrets、HashiCorp Vault等专业秘钥管理工具。在CI/CD流程中动态注入，避免将秘钥硬编码在镜像或配置文件中。
- 为每个内部服务分配一个ClientId和ClientSecret，它们之间的调用通过OAuth 2.0的Client Credentials流程获取访问令牌。访问令牌格式与用户登录获取的JWT Token一致，但其与登录Token不同的是获取流程、携带信息与过期时间，且不支持刷新令牌
- 多活与容灾架构：
	- 认证服务作为核心基础设施，必须支持多机房容灾甚至异地多活。当一个数据中心故障时，用户登录不受影响。
	- 分级降级策略：
		- 在极端情况下，允许已签发且在有效期内的JWT令牌继续访问非核心的只读服务（如博客浏览），但会暂停登录、支付等核心写操作，并有一个极简的静态故障页面提供基本信息和公告。
		- 一级降级：短信服务商A失败，立即切换至预置的备用服务商B。
		- 二级降级：所有服务商均不可用，启动备用认证流程：
			1. 引导用户使用邮箱验证码
			2. 若邮箱也未绑定，则触发基于预设安全问题的验证（问题在注册时设置）
			3. 最终兜底为人工客服审核
		- 前端感知后端服务的健康状态并实现降级：
			- 通过前端可观测性SDK和降级编排。
			- SDK会监控API调用的成功率和延迟。同时，后端服务通过健康检查接口（如/health）上报状态。
			- 当检测到推荐服务不可用，前端不是简单报错，而是自动切换UI布局，例如：
				1. 隐藏“智能推荐”板块；
				2. 扩大展示“我的常用服务”和“平台热门服务”区域。这需要前端设计阶段就考虑各组件的降级展示逻辑。
			- 对于网速极慢的用户，优先加载核心内容和功能，复杂的动画和图片后续加载。
- 风险感知自适应认证：
	- 实时评估登录行为风险，对于低风险登录，简化验证；对于高风险行为，强制进行二次验证。
	- 行为分析：比较本次恢复请求与用户历史行为（IP段、设备指纹、请求时间）
	- 申诉历史：检查该账号是否有异常的频繁申诉记录。
- 敏感配置（如密码、密钥）由配置中心对接KMS进行加密存储，应用启动时动态解密：
	- 所有密钥、证书集中存储在KMS中，应用通过临时令牌动态获取。除特殊情况外，不支持在线手动管理密钥。
	- 轮换策略：
		- JWT签名密钥：采用双密钥机制（当前+上一代），无缝轮换，无需下线服务。
		- OAuth Client Secret：支持在线重新生成，旧Secret保留24小时失效宽限期。
		- 数据库加密主密钥：轮换后，数据在后台异步重新加密，读取时先用新密码尝试，失败再用旧密码。
